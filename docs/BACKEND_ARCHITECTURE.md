# Architecture backend (hôte C#)

L'hôte est une application C# .NET 10 avec une fenêtre WinUI 3 (Windows App SDK, non empaquetée) qui héberge une seule WebView2. Il ne porte aucune interface métier : il gère la fenêtre, les terminaux, la persistance et les services locaux. L'interface entière est dans `web/`.

## Projets

| Projet | Rôle |
| --- | --- |
| `src/Tily.Core` | Bibliothèque sans interface, testable : pseudo-consoles, Job Objects, intégration shell, modèle et persistance de session. Aucune dépendance WinUI ; seule dépendance externe : `Microsoft.Data.SqlClient`, pour répliquer une base SQL Server de worktree. |
| `src/Tily.Host` | Fenêtre WinUI 3, WebView2, pont hôte / web. Contient le moins de logique possible. |
| `src/Tily.Mcp` | Exécutable console `tily-mcp.exe` : serveur MCP stdio (SDK `ModelContextProtocol.Core`) lancé par Claude Code, qui relaie chaque outil à son instance de Tily par le named pipe de `Tily.Core/Mcp` : `tily_layout`, `tily_read_pane`, `tily_commands`, `tily_wait_for` (`TilyTools`, arguments bornés avant envoi, version annoncée lue sur le `Tily.dll` voisin), `tily_open_workspace`, `tily_new_tab`, `tily_split`, `tily_focus`, `tily_rename`, `tily_run`, `tily_interrupt`, `tily_close` (`TilyActions`, dossiers et commandes vérifiés avant envoi), `tily_worktrees`, `tily_create_worktree`, `tily_remove_worktree` (`TilyWorktreeTools`, dépôt par défaut : dossier courant de l'agent). Lancé hors de Tily (`McpEndpoint.PaneFromEnvironment` nul, faute de `TILY_PANE_ID`), il ne déclare ni outil ni instruction : rien n'entre dans le contexte de Claude. Il s'arrête quand Claude Code ferme son entrée standard, à la fin de la session. Référencé par `Tily.Host`, il est construit et publié dans le même dossier que `Tily.exe` et partage son runtime .NET. |
| `tests/Tily.Core.Tests` | Tests xUnit de `Tily.Core` (voir `docs/TESTING.md`). |

`Directory.Build.props` à la racine fixe `Nullable`, `ImplicitUsings`, la plateforme x64 et `win-x64`.

Règles :

- L'hôte est la source de vérité de la session persistée : le web envoie la session complète, l'hôte la valide avant d'écrire. Chaque `session.save` ou `text.save` répond `session.saved`, ou `session.saveFailed {message}` (session refusée, disque ou droits) sans faire tomber la session en cours.
- Au démarrage, `app.hello` porte `recovery` quand `session.json` ou `text.json` a été mis en quarantaine ; la session de secours est alors l'avant-dernier enregistrement (`session.previous.json`, copié avant chaque écriture de `session.json` ; si cette copie échoue, l'écriture a lieu quand même et l'ancienne copie reste) s'il est valide, sinon la session initiale, et le fichier fautif reste à côté pour récupération. `AtomicFile` force l'écriture du fichier temporaire sur le disque (`Flush(true)`) avant de le renommer, pour qu'une coupure de courant ne laisse pas un fichier vide.
- Le texte restauré n'est qu'un affichage : les shells sont toujours relancés neufs, aucune commande n'est rejouée.
- `settings.export` ouvre un sélecteur d'enregistrement (`.json`, nom proposé `tily-preferences`) et écrit la configuration enregistrée ; `settings.import` ouvre un sélecteur de fichier `.json`, valide le contenu et renvoie `settings.imported` sans écrire, avec dans `warnings` chaque valeur de persistance hors bornes ramenée dans sa plage (`PersistenceSettingsModel.OutOfRangeWarnings`) : l'application effective passe par `settings.save`, ce qui vaut confirmation et remplace la configuration (aucune fusion). Un fichier refusé remonte en `error`.
- `settings.save` valide, écrit les quatre fichiers puis applique immédiatement : nouveaux chemins de shells pour les prochains `terminal.create` (les shells déjà lancés ne bougent pas), nouvelle commande d'éditeur, nouvelle racine des projets, nouvelle limite d'historique. Un réglage refusé remonte en `error` sans rien écrire.
- Chaque pane est rattaché à un Job Object avec `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` : fermer un pane (`terminal.close`), un onglet, un workspace ou l'application termine de force tout son arbre de processus, y compris les enfants détachés du shell. Aucun service persistant ne reprend les anciens agents ou serveurs.
- Avant une fermeture, le web demande `terminal.activity {panes}` ; l'hôte répond `terminal.activityResult` avec les panes qui ont encore des programmes actifs (noms de processus) et renvoie tel quel le numéro `request` reçu (0 sans numéro), qui distingue les demandes du serveur MCP de celles de la confirmation de fermeture. Le web affiche alors une confirmation ciblée ; l'hôte n'arrête rien tant que le web n'envoie pas `terminal.close` ou `window.close`. `app.closing` porte directement cette activité pour tous les panes vivants.
- L'environnement transmis au shell ajoute `TILY_TERMINAL=1`, `TILY_PANE_ID` et `TERM_PROGRAM=TilyTerminal`, et retire toute variable `WEZTERM_*`. Un `TILY_DATA_DIR` défini est réécrit en chemin absolu au démarrage de l'hôte, pour que le hook et `tily-mcp.exe`, lancés depuis un autre dossier, retrouvent la même instance.
- Plusieurs fenêtres : chaque fenêtre est un processus `Tily.exe` avec sa propre session (`SessionStore`) ; préférences, états d'agents, demandes d'aperçu et téléchargements de mise à jour restent dans le dossier de données commun. Une fenêtre ne lit et ne supprime que les fichiers de ses propres panes (identifiants uniques) et ne purge les dossiers partagés qu'au démarrage à froid, quand aucune autre fenêtre n'est ouverte.
- États des agents : l'hôte purge `agents\*.json` au démarrage à froid, et l'état d'un pane à chaque `terminal.create` et `terminal.close` (aucun état ancien n'est restauré comme vivant : un fichier plus ancien que le shell du pane est de toute façon ignoré), puis évalue `AgentMonitor.Resolve(_terminals.Probes())` hors du thread UI toutes les 2 s et au plus 150 ms après un changement du dossier `agents` (`FileSystemWatcher`, changements rapprochés regroupés en une seule évaluation). Il envoie `agent.states {panes[{paneId, agent, state, message?, detail?, interrupted?, sessionId?}]}` seulement quand le résultat change ; un pane absent de la liste n'a aucun agent. Le script `hooks\tily-agent-state.ps1`, copié à côté de `Tily.exe`, est le producteur Claude Code : appelé par les hooks `SessionStart` (inconnu), `UserPromptSubmit` et `PostToolUse` (en cours), `PreToolUse` limité par `matcher` à `AskUserQuestion`, `PermissionRequest` et `Notification` de type `permission_prompt`, `elicitation_dialog` ou `agent_needs_input` (en attente : une réponse est réellement requise ; la notification d'inactivité `idle_prompt` est ignorée pour ne pas confondre attente et fin de tour), `Stop` (terminé, avec en `detail` le dernier texte de Claude : `last_assistant_message` s'il est fourni, sinon la dernière réponse hors sous-agent parmi les 200 dernières lignes du transcript), `StopFailure` (en erreur), `SessionEnd` (suppression du fichier), il lit `TILY_PANE_ID` hérité du shell et écrit le fichier du pane ; un second groupe `PreToolUse`, `matcher` `Bash` filtré par `"if": "Bash(start *)"` (`ClaudeHooksInstaller.PreviewCommandCondition`, PowerShell n'est donc lancé que pour une commande `start`), intercepte l'ouverture d'une page HTML : une commande réduite à `start [""] <chemin>.html` (`.htm` compris, chemin entre guillemets doubles, simples ou sans espace, Git Bash `/c/…`, `~/…`, Windows ou relatif au `cwd` du hook) vers un fichier existant dépose `previews\<pane>-<guid>.json` (écrit en `.tmp` puis renommé) et répond `permissionDecision: deny` avec une raison en français qui dit à Claude que Tily a ouvert le fichier ; toute autre commande (enchaînée, autre extension, fichier absent) passe sans réponse ; les messages sont des libellés français fixes (jamais le texte anglais de Claude), une notification d'attente n'écrase pas une attente déjà signalée par `PermissionRequest`, et le script porte un BOM UTF-8 pour que Windows PowerShell 5.1 lise ses accents. `ClaudeHooksInstaller` (`Status`, `Install`, `Remove`) fusionne ou retire ces hooks dans `%USERPROFILE%\.claude\settings.json` uniquement sur `agents.installHooks` / `agents.removeHooks` (clic explicite dans Paramètres) : les autres clés et les hooks étrangers sont conservés, un groupe Tily est reconnu par le chemin de `tily-agent-state.ps1`, `Status` exige chaque groupe attendu avec son `matcher` et son `if` (des hooks installés par une version antérieure sont donc annoncés « non installés » jusqu'à une nouvelle installation), l'écriture est atomique ; un fichier illisible remonte en `error` sans être touché (ses commentaires JSON éventuels ne survivent pas à une réécriture). Chaque opération répond par un `settings.result` à jour. Codex CLI n'a pas de producteur : « Inconnu » seulement.
- Serveur MCP : `McpFeed` lit l'état de la déclaration hors du thread UI au démarrage et n'ouvre le pipe de l'instance que si le serveur est déclaré ; `mcp.install` / `mcp.remove` (clic dans Paramètres) déclarent ou retirent le serveur, ouvrent ou ferment le pipe et répondent par `settings.result`. Chaque appel reçu sur le pipe devient `mcp.request {id, tool, pane, arguments?}` vers le web ; la réponse `mcp.response {id, result | error}` le termine ; sans réponse en 10 s (pour `waitFor`, `McpWaitFor.AnswerTimeout` ; pour `run`, `interrupt` et `close`, qui peuvent attendre l'accord de l'utilisateur, `McpActions.ConsentAnswerTimeout` ; pour `createWorktree` et `removeWorktree`, `McpWorktrees.OperationAnswerTimeout`), l'appel échoue en français ; avant `app.ready`, il échoue avec « Tily démarre encore ». Le thread UI ne fait que poster des messages : l'attente se fait sur le pool de threads. L'hôte ajoute la branche de chaque pane à la réponse de `layout`. Le pane appelant vient de `TILY_PANE_ID`, hérité par Claude Code puis par `tily-mcp.exe`.
- Mises à jour : l'hôte vérifie la dernière release 10 s après le lancement puis toutes les 6 h tant que `updates.autoCheck` est vrai (réglage appliqué dès `settings.save`), et à chaque `update.check`. Rien n'est téléchargé sans `update.install`, refusé en `error` pour une copie non installée ; l'installeur va dans le sous-dossier `updates` du dossier de données, vidé au démarrage à froid (aucune autre fenêtre de Tily ouverte). `update.apply` n'est accepté que si l'installeur vérifié existe encore (sinon `error` et retour à l'état « disponible ») : l'hôte retient alors l'installeur et répond `update.restart`, le web ferme l'application comme d'habitude (disposition et texte envoyés, puis `window.close`) et l'installeur n'est lancé qu'à la fin de `HostBridge.Dispose`, terminaux arrêtés. L'installeur attend la fin du processus Tily (30 s au plus) avant de copier les fichiers, puis relance `Tily.exe` avec les droits de l'utilisateur d'origine.
- Worktrees : Tily en porte une version native (`Worktrees/`, `WorktreeFeed`) ; `wtr` / `rmwt` restent chargés par le profil et utilisables au terminal avec les mêmes chemins. L'hôte ne crée ni ne ferme jamais de workspace : il annonce `worktrees.created`, le web ouvre le workspace.
- Contrat de synchronisation worktrees : pour un `wtr` / `rmwt` tapé au terminal, l'hôte ne rejoue aucun effet. Après `wtr`, le prompt du pane émet OSC 7 avec le nouveau dossier (`terminal.cwd`), rien d'autre. Après `rmwt`, à chaque `terminal.cwd` reçu de n'importe quel pane, `TerminalManager.MissingDirectories` vérifie le dossier courant de toutes les sessions vivantes et l'hôte envoie `terminal.pathMissing {pane, path, fallback}` pour celles dont le dossier a disparu ; même message à `terminal.create` si le dossier demandé n'existe plus (le shell démarre alors dans le dossier utilisateur). Aucun pane ni workspace n'est fermé ou créé automatiquement.
- Un échec de `terminal.create` remonte en `error` avec le `pane` concerné ; le web affiche alors un état local au pane (relance, choix d'un autre shell, fermeture). Seul l'échec d'une commande `terminal.*` porte ce `pane` : une autre commande qui en cite un (`context.open`, `attention.raise`…) remonte en `error` sans lui, pour ne jamais présenter un shell vivant comme arrêté.

## Construction

- `dotnet build Tily.slnx` construit tout. La cible `BuildWeb` de `Tily.Host.csproj` lance `pnpm install` et `pnpm build` si `web/dist/index.html` est absent ou en configuration Release, puis `CopyWebToOutput` copie `web/dist` dans `wwwroot/` du dossier de sortie.
- Publication autonome : `dotnet publish src/Tily.Host/Tily.Host.csproj -c Release -r win-x64 -p:Platform=x64 --self-contained -o publish`. `EnableMsixTooling` est requis pour que le `.pri` soit publié. `tily-mcp.exe` (projet `Tily.Mcp`, référencé par l'hôte) est publié dans le même dossier, avec ses dépendances, sans second runtime.
- Installeur : `scripts/build-installer.cmd` lit la version de `Tily.Host.csproj`, publie dans `publish/`, télécharge le programme d'installation WebView2 Evergreen puis compile `installer/Tily.iss` avec Inno Setup 6 vers `installer/output/Tily-<version>-setup.exe`. Installation par utilisateur sans droits administrateur (`%LOCALAPPDATA%\Programs\Tily`, élévation proposée en option), WebView2 installé seulement s'il manque, raccourci dans le menu Démarrer et raccourci Bureau optionnel. À la désinstallation, `Tily.exe --remove-claude-hooks` retire les hooks Tily de `settings.json` de Claude Code s'il y en a (`ClaudeHooksInstaller.RemoveIfPresent`, fichier non réécrit sinon) et la déclaration du serveur MCP `tily` de `.claude.json` (`ClaudeMcpInstaller.RemoveIfPresent`), puis une question propose de supprimer `%LOCALAPPDATA%\Tily` (non par défaut, conservé en désinstallation silencieuse). L'installeur n'est pas signé : SmartScreen avertit au premier lancement. Pour les mises à jour depuis Tily, `InitializeSetup` attend la fin du processus passé en `/WAITPID` et `/RELAUNCH=1` relance `Tily.exe` en fin d'installation (`runasoriginaluser`) ; `/ALLUSERS` et `/CURRENTUSER` sont acceptés en ligne de commande.
- Release : monter `<Version>` dans `Tily.Host.csproj`, lancer le script, puis `gh release create v<version> installer/output/Tily-<version>-setup.exe --generate-notes`. Garder le nom `Tily-<version>-setup.exe` et le tag `v<version>` : la mise à jour intégrée cherche cet installeur dans la dernière release publiée et affiche la section « Nouveautés » de ses notes.
- Développement web à chaud : `pnpm dev` dans `web/`, puis lancer l'hôte avec `TILY_WEB_DEV_URL=http://localhost:5173`.
- Instance isolée : `TILY_DATA_DIR=<chemin absolu>` fait lire et écrire sessions, texte, réglages, états d'agents et profil WebView2 dans ce dossier. Plusieurs fenêtres d'une même copie de Tily n'en ont pas besoin (une session chacune), mais une version de développement lancée pendant qu'un Tily installé tourne doit l'utiliser, pour ne partager ni ses réglages ni son profil WebView2.

## Conventions

- Messages d'erreur en français (les termes Git restent en anglais et invariables : push, pull, fetch, stash, stage, merge, rebase, amend, checkout, cherry-pick), suffixe `Model` pour les classes de données, suffixe `Async` pour les méthodes asynchrones, aucun commentaire dans le code, fichiers de moins de 400 lignes.
- Les erreurs attendues du pont remontent en `error` au web ; les exceptions inattendues ne doivent pas faire tomber l'hôte.
